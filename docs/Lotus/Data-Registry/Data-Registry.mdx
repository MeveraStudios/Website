# Data Registry

`DataRegistry` is Lotus's type-safe container for **per-view** and **per-button** state. It replaces the `Map<String, Object>` pattern you'd otherwise reach for, with runtime type checks on both insert and read.

## `Key<T>` — typed identifiers

A `Key<T>` is a typed identifier: the type is metadata, the **identity is the name**.

```java
public final class Keys {
    public static final Key<Integer> PAGE     = Key.of("page",     Integer.class);
    public static final Key<UUID>    TARGET   = Key.of("target",   UUID.class);
    public static final Key<String>  CATEGORY = Key.of("category", String.class);
}
```

:::tip
Declare keys as `public static final` constants in a central `Keys` class. Two keys are equal if their names match — define each key **once per concept** and reuse it everywhere.
:::

## `DataRegistry` — the container

```java
DataRegistry data = DataRegistry.empty();

data.put(Keys.PAGE, 2);
data.put(Keys.TARGET, player.getUniqueId());

int page              = data.require(Keys.PAGE);    // throws if missing
Optional<UUID> target = data.get(Keys.TARGET);      // null-safe
boolean hasPage       = data.contains(Keys.PAGE);
data.remove(Keys.PAGE);
```

:::caution
Type checks run **both** on insert and on read — a wrong-typed value fails fast with a `ClassCastException` instead of becoming a mysterious `NullPointerException` somewhere downstream.
:::

## Where registries live

### Per-view data

Every `MenuView` owns a registry. Seed it when opening the menu:

```java
DataRegistry seed = DataRegistry.empty()
    .put(Keys.TARGET, target.getUniqueId());

lotus.openMenu(player, menu, seed);
```

Read it from any hook:

```java
@Override public @NotNull Content content(MenuView<?> view) {
    UUID target = view.data().require(Keys.TARGET);
    ...
}
```

### Per-button data

Every `Button` has its own registry too. Stamp each button with the model it represents, then read it back on click:

```java
Button entry = Button.clickable(head(someone), (view, event) -> {
    view.content().get(Slot.of(event.getSlot()))
        .flatMap(b -> b.data().get(Keys.TARGET))
        .ifPresent(uuid -> inspect(uuid));
});
entry.data().put(Keys.TARGET, someone.getUniqueId());
```

This pattern scales especially well in **pagination** — the renderer stamps each item button with its backing model's ID, and a single click handler can recover the model from any slot.

## Idioms

**Defaults** — use `get(...).orElse(...)`:

```java
int page = view.data().get(Keys.PAGE).orElse(0);
```

**Required invariants** — use `require(...)`:

```java
UUID target = view.data().require(Keys.TARGET);   // a missing value is a bug
```

**Mutate inside a click handler** — the registry is mutable; changes persist for the life of the view:

```java
view.data().put(Keys.PAGE, view.data().require(Keys.PAGE) + 1);
view.refresh();   // re-resolve content with the new state
```

## What **not** to do

:::danger{label="Anti-patterns"}
- **Don't share** a single `DataRegistry` between views. One per view, one per button. The framework handles this for you — don't smuggle references around.
- **Don't use it for cross-player state.** It's per-view. Global plugin state lives in your plugin, not in Lotus.
- **Don't abuse keys as message passing.** If it's a click → action flow, a `ClickAction` closure captures its data naturally. Keys are for data that outlives any one click.
:::
